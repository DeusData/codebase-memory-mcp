# cbm 架构说明（聚焦语言解析）

> 本文以仓库当前工作树（`dev_zzc`，2026-10）的代码为准，路径均相对仓库根目录。
> 相关文档：`docs/llms.txt`（对外能力概览）、`docs/JAVA-HASHUID.md`（TrackerV2 身份）、
> `docs/CONFIGURATION.md`（配置与运行模式）、`docs/cbmignore.md`（忽略规则）。

## 0. 阅读指南

本文回答三个问题：

1. cbm 从仓库到知识图谱的整体架构是什么；
2. **多语言解析**是怎么组织的（重点）；
3. 要新增一门语言，或给某种语言加语言相关的后处理，应该动哪些文件。

## 1. 系统总览

cbm（codebase-memory-mcp）是一个 C 实现的本地索引器 + MCP 服务：把代码仓解析成
持久化的图（SQLite），再通过 MCP / CLI / 守护进程 / 图 UI 对外提供结构查询。

```
         ┌─ src/cli ──────────┐
入口面 ──┼─ src/mcp (MCP srv) ├──▶ 统一索引入口 cbm_pipeline_run (src/pipeline/pipeline.c)
         ├─ src/daemon ───────┤                │
         └─ src/ui / graph-ui ┘                ▼
                                    discover（文件清单 + 语言判定）
                                              │
                                    parse + extract（每文件一个 CBMFileResult）
                                       │                    │
                          并行：worker 各自 gbuf       语言特化的 LSP / 预处理
                                       └────► merge ───────┘
                                              ▼
                                    graph_buffer（内存图：nodes/edges + QN 索引）
                                              │
                                    predump passes（解析/相似度/语义/身份）
                                              ▼
                                    store（SQLite：nodes / edges / …）
                                              │
                                    MCP 查询 / Cypher / UI / 导出
```

分层职责：

| 层 | 位置 | 职责 |
|---|---|---|
| 入口 | `src/cli/`、`src/mcp/`、`src/daemon/`、`src/ui/` | CLI 子命令、MCP 工具、守护进程、图 UI 数据 |
| 编排 | `src/pipeline/pipeline.c` | 一次索引的全部阶段：发现、抽取、解析、pass、落库 |
| 发现 | `src/discover/` | 文件遍历、忽略规则（`.cbmignore`/`.gitignore`）、**语言判定**、用户扩展名配置 |
| 解析/抽取 | `internal/cbm/` | tree-sitter 语法注册、单文件解析、各语言抽取器、LSP 类型解析 |
| 图 | `src/graph_buffer/` | 内存图（节点/边、QN 索引、去重、worker 合并） |
| 后处理 | `src/pipeline/pass_*.c` | 调用解析、类型引用、相似度、复杂度、测试、重要度、HashUID 等 |
| 存储 | `src/store/`、`internal/cbm/sqlite_writer.c` | SQLite schema、读写路径、增量与索引格式版本 |
| 语义检索 | `src/semantic/`、`src/simhash/` | 本地向量（nomic-embed-code）与 MinHash 近克隆 |

## 2. 索引流水线（`src/pipeline/pipeline.c`）

### 2.1 阶段一览

`cbm_pipeline_run_staged()` 按固定顺序执行：

1. **准备**：刷新 git 上下文；加载用户扩展名配置（`cbm_userconfig_load`）；
   按模式打开/关闭 C/C++ 宏节点抽取（`cbm_set_macro_extraction`，仅 FULL）。
2. **发现**：`cbm_discover_ex2()` 产出 `cbm_file_info_t[]`，每个文件带
   `language`（**后续所有阶段都以这个语言为键**）；同时记录被排除的目录与被忽略的文件。
3. **语义 manifest 与增量路由**：对全部语义输入做一次快照哈希，然后
   `try_incremental_or_delete_db()` 决定走全量重建 / legacy-partial / closure-delta，
   或因为索引格式版本不兼容直接重建（`CBM_INDEX_FORMAT_VERSION`，当前 v2）。
4. **structure pass**：先建 Project/Folder/Package/File 等结构节点。
5. **抽取阶段**（`run_extraction_phase`）：
   - worker 数 > 1 且文件数 > `MIN_FILES_FOR_PARALLEL`（50）时走并行，否则串行；
   - 串行路线依次跑 6 个 pass：`definitions → k8s → lsp_cross → calls → usages → semantic`；
   - 并行路线每个 worker 用独立 `gbuf` 抽取，最后按 QN 合并（冲突时 src 覆盖 dst）。
6. **测试与 git 历史**（`run_tests_and_history`）：`pass_tests`、`pass_githistory`。
7. **predump passes**（`run_predump_passes`，顺序固定）：
   `decorator_tags → configlink → route_match → ensemble_routing → similarity →
   semantic_edges → complexity → importance → hashuid`；
   其中 `similarity`/`semantic_edges` 在 FAST 模式跳过；`importance` 必须在
   TESTS/CALLS/USAGE 之后；`hashuid` 固定放在最后（它只读抽取期属性 + 容器节点，
   且必须等所有文件抽完）。
8. **落库与发布**（`dump_and_persist_hashes`）：写 SQLite、发布新代际、按需导出
   `.codebase-memory/graph.db.zst` 压缩产物。

每个阶段都检查取消标志；失败用返回值区分「保留上一代数据库」与「本次失败」。

### 2.2 索引模式

`cbm_index_mode_t`（`src/pipeline/pipeline.h`）：

| 模式 | 含义 |
|---|---|
| `CBM_MODE_FULL` | 全部文件与全部边：含 SIMILAR_TO / SEMANTICALLY_RELATED，含 C/C++ 宏节点 |
| `CBM_MODE_MODERATE` | 快速发现 + 仍然计算相似度/语义边（跳过宏节点等重抽取） |
| `CBM_MODE_FAST` | 跳过非必要文件，不计算相似度/语义边 |

三种模式**都**会跑每文件与跨文件的 LSP 类型解析；模式只控制发现广度和
相似度/语义边、宏节点这类重负载项。

### 2.3 增量

- `closure-delta`：只重抽改动文件的闭包，用 SQL patch 合并回库；**不跑 HashUID**
  （其容器可能缺失，会写出错误的 `logical_module`）。
- `legacy-partial`：把整项目 rehydrate 回 `gbuf` 再重抽改动文件，可跑
  `importance` 与 `hashuid`（判定条件与 `score_importance` 同源）。
- 两种路线都由 `file_hashes` / 语义 manifest 驱动，见 `src/pipeline/pipeline_incremental.c`。

## 3. 语言解析架构（重点）

### 3.1 四个层次

```
① 识别     src/discover/language.c       扩展名/文件名/shebang → CBMLanguage 枚举
①' 覆盖    src/discover/userconfig.c     用户配置 extra_extensions 覆盖判定
② 规格     internal/cbm/lang_specs.c     CBMLanguage → 各节点类型名数组 + 语法工厂
③ 语法     internal/cbm/grammar_*.c      每语言一个 unity 单元（内含 vendored parser.c）
           internal/cbm/ts_runtime.c     vendored tree-sitter 运行时（v0.26，DeusData fork）
④ 抽取     internal/cbm/extract_*.c      表驱动 + 语言分支 + 专用抽取器
           internal/cbm/lsp/、lsp_all.c   语言族的轻量 LSP 类型解析
                                          （Py / TS-JS / PHP / C# / Go / C-C++ /
                                            Java / Kotlin / Rust，另有 Perl）
```

**关键结论**：语法层是"一语言一语法、彼此独立"；抽取层是"一套共享框架 + 每语言
规格与分支"。新增一门语言的主要工作量在 ② 的表行和 ④ 的特例，而不是新写一个解析器
（语法本身是 vendored 的 tree-sitter 产物）。

### 3.2 语言识别（`src/discover/`）

- `language.c`：`cbm_language_for_filename()` / `cbm_language_for_extension()`。
  判定顺序大致是：文件名特判（`Dockerfile`、`Makefile`、`CMakeLists.txt` 等）→
  扩展名表 → shebang（`cbm_language_from_shebang`）；对二义性后缀有专门的消解函数：
  `.m`（MATLAB/ObjC）、`.frm`、`.cls`（ObjectScript/Apex/…）、`.inc`、`.cfc`。
- `userconfig.c`：读取 `{repo_root}/.codebase-memory.json`（项目级）与
  `$XDG_CONFIG_HOME/codebase-memory-mcp/config.json`（全局级）的 `extra_extensions`，
  项目级优先；未知语言值告警并跳过（fail-open）。
- 判定结果写进 `cbm_file_info_t.language`，抽取、LSP、pass、增量都以它为准。

### 3.3 语言规格表（`internal/cbm/lang_specs.c/.h`）

`CBMLangSpec` 是"语言 → 该语言在 AST 里长什么样"的声明式描述：

```c
typedef struct {
    CBMLanguage language;
    const char **function_node_types;   // 函数/方法定义节点
    const char **class_node_types;      // 类/结构体/接口/枚举定义节点
    const char **field_node_types;
    const char **module_node_types;
    const char **call_node_types;       // 调用表达式节点
    const char **import_node_types;
    const char **import_from_types;
    const char **branching_node_types;  // if/switch 等（复杂度、作用域）
    const char **variable_node_types;
    const char **assignment_node_types;
    const char **throw_node_types;
    const char *throws_clause_field;
    const char **decorator_node_types;
    const char **env_access_functions;        // 读环境变量的函数名
    const char **env_access_member_patterns;
    const TSLanguage *(*ts_factory)(void);    // 语法工厂（extern tree_sitter_xxx）
    const CBMEmbeddedLangSpec *embedded_imports; // 宿主语法里的嵌入语言
} CBMLangSpec;
```

要点：

- 表是 `static const CBMLangSpec lang_specs[CBM_LANG_COUNT]`，用指定初始化器
  `[CBM_LANG_XXX] = {...}` 按枚举下标落座，并有
  `_Static_assert(sizeof(lang_specs)/sizeof(lang_specs[0]) == CBM_LANG_COUNT, …)`
  兜底；枚举顺序必须与表一致（`internal/cbm/cbm.h` 顶部有注释强调）。
- 取用入口只有两个：`cbm_lang_spec(lang)`（校验 `spec->language == lang` 且
  `function_node_types` 非空）与 `cbm_ts_language(lang)`（调用 `ts_factory`）。
- `embedded_imports` 描述"宿主语法不递归解析的嵌入内容"：例如 Vue/Svelte/Astro 的
  `<script>` 是 `raw_text`，由通用 walker 定位 `script_node_type` 后取
  `content_node_type` 切片，再用 `embedded_language` 的语法重解析，让既有的
  JS/TS 抽取器直接复用。
- 少数语言是"零规格"行：例如 `CBM_LANG_OBJECTSCRIPT_EXPORT`（Studio Export XML）
  不在表里配语法，而是由 `iris_export_xml.c` 转码成 UDL 后按
  `CBM_LANG_OBJECTSCRIPT_UDL` 重新抽取。

### 3.4 语法本体与构建

- 每个语言一个包装文件 `internal/cbm/grammar_<lang>.c`，内容就是一行 unity include：

  ```c
  // Vendored tree-sitter grammar: java
  // Each grammar compiled as separate unit (conflicting static symbols).
  #include "vendored/grammars/java/parser.c"
  ```

  当前有 162 个这样的文件。**独立编译单元是必须的**：tree-sitter 生成的解析表带大量
  同名 `static` 符号，合并编译会冲突。
- 语法本体在 `internal/cbm/vendored/grammars/<lang>/`（部分语言还带 `scanner.c`）。
- 运行时在 `internal/cbm/ts_runtime.c`（单文件 include vendored tree-sitter v0.26 的
  `src/lib.c`），与语法分开编译。
- `lang_specs.c` 顶部逐个 `extern const TSLanguage *tree_sitter_xxx(void);` 声明工厂符号，
  链接期解析到对应 grammar 对象。
- `Makefile.cbm` 用 `GRAMMAR_SRCS = $(wildcard $(CBM_DIR)/grammar_*.c)` 收集，
  新增包装文件无需改构建脚本；且每个 grammar 对象通过二级展开（`.SECONDEXPANSION`）
  把自身 vendored 目录下的 `.c/.h` 声明为前置依赖——改 vendored scanner 会触发重编，
  不会再出现"源码改了、二进制里还是旧符号"的陷阱。

### 3.5 单文件解析与抽取流程（`internal/cbm/cbm.c`）

入口 `cbm_extract_file()` / `cbm_extract_file_ex()` → `extract_file_ex_body()`：

1. **隔离检查**：命中 crash quarantine 的文件直接返回空结果，不再解析。
2. **查规格**：`cbm_lang_spec()` / `cbm_ts_language()`；查不到 → 带错误的空结果。
3. **病态输入前置拦截**：例如 Perl 的嵌套深度超限直接在 tree-sitter 之前拒绝
   （避免递归 GLR 栈溢出）。
4. **解析**：取本线程复用的 parser（`get_thread_parser`，按语言重绑语法）→
   `ts_parser_parse_with_options`。每文件有解析预算：**CPU 时间 deadline + 宽松 wall
   ceiling** 双保险，超时与解析失败用不同的 `error_msg` 区分。
5. **文件级元数据**：`result->module_qn = cbm_fqn_module_source_lang(...)`（Java/Go 用
   目录推导模块，其它语言保留原规则）、`is_test_file` 判定。
6. **三次 AST 走查**（同一个 `CBMExtractCtx`）：
   - `cbm_extract_definitions()`：定义（Function/Method/Class/…）；
   - `cbm_extract_imports()`：导入；
   - `cbm_extract_unified()`：一次游标 walk 内派发 7 个 handler ——
     `handle_calls / handle_usages / handle_throws / handle_readwrites /
     handle_type_refs / handle_env_accesses / handle_type_assigns`，
     并在 walk 中维护作用域栈（函数/类/循环/分支/词法作用域）。
7. **语言/文件族专用抽取**：`cbm_extract_channels()`（JS/TS 的 Socket.IO/EventEmitter
   等 pub/sub）、K8s/Kustomize 清单、dbt（Jinja SQL）血缘。
8. **LSP 类型解析**（每文件，所有模式）：按语言分派到
   `cbm_run_go_lsp / c_lsp / php_lsp / perl_lsp / py_lsp / ts_lsp / cs_lsp /
   java_lsp / kotlin_lsp / rust_lsp`，产出 `resolved_calls` 等类型感知结果。
9. **C/C++ 第二遍**：对 raw 树抽完后，用 `cbm_preprocess_with_map()` 做宏展开、
   `#ifdef` 求值、`#include` 解析，得到 expanded 源码与
   `original_line_by_expanded_line` / `belongs_to_main_file` 行映射；对 expanded 源码
   再解析、再跑 unified 与 C LSP，然后把行号映射回原始文件行并合并进同一个结果
   （`pp_ctx`）。展开自 include/宏的内容靠 `belongs_to_main_file` 过滤，
   只有映射回主文件的行进入图。
10. **结果 compact**：`cbm_result_compact()` 把工作 arena 压成精确大小的结果 arena，
    控制大仓内存；超大结果走 `result_spill`。

### 3.6 抽取器分工

| 文件 | 产出 |
|---|---|
| `internal/cbm/extract_defs.c` | 定义节点（函数/方法/类/结构体/枚举/…），体量最大，含各语言分支与签名/命名规则 |
| `internal/cbm/extract_imports.c` | IMPORTS 边与模块解析（含嵌入式语言重解析） |
| `internal/cbm/extract_unified.c` | 单次游标 walk，派发 calls/usages/throws/readwrites/type_refs/env_accesses/type_assigns 七个 handler，维护作用域与词法绑定 |
| `internal/cbm/extract_calls.c` | callee 解析、字符串派发（`cbm_string_dispatch_suffixes`）等调用语义 |
| `internal/cbm/extract_usages.c` | USAGE 边、词法作用域绑定与遮蔽判定 |
| `internal/cbm/extract_type_refs.c` / `extract_type_assigns.c` | 类型引用与类型赋值 |
| `internal/cbm/extract_semantic.c` | 语义信号（供 SEMANTICALLY_RELATED 等） |
| `internal/cbm/extract_env_accesses.c` | 环境变量读写 |
| `internal/cbm/extract_channels.c` | pub/sub 通道（JS/TS 系） |
| `internal/cbm/extract_dbt.c` / `extract_k8s.c` | dbt 血缘 / K8s 与 Kustomize |
| `internal/cbm/lsp_all.c` + `internal/cbm/lsp/` | 各语言族的类型解析实现（Py / TS-JS / PHP / C# / Go / C-C++ / Java / Kotlin / Rust / Perl） |
| `internal/cbm/preprocessor.cpp`、`macro_table.c`、`iris_export_xml.c` | C/C++ 预处理、ObjectScript `$$$` 宏表、Studio Export XML 转码 |

### 3.7 语言差异的三种落地形态

1. **表驱动**（首选）：节点类型名进 `lang_specs.c` 的数组，抽取器通用逻辑即可工作。
2. **集中分支**：`extract_defs.c`、`extract_calls.c` 等文件里按
   `ctx->language == CBM_LANG_XXX` 走特例（Java 在 `extract_defs.c` 就有十余处判断，
   例如 `spread_parameter` 的签名处理、字段名提取）。
3. **专用模块/后处理**：语义确实特殊时才做——ObjectScript（宏表 + Export XML 转码）、
   C/C++（双遍预处理）、dbt/K8s、以及各语言族的 LSP 实现。

加语言时的经验法则：先把 1 做足，只有当该语言的**结构语义**（不是节点名词）真正
特殊时才引入 2/3，否则会把这个"共享框架"切碎。

### 3.8 命名与模块语义

- 每个文件先算出 `module_qn`（`cbm_fqn_module_source_lang`）：Java/Go 按**目录**
  推导（package 语义），其它语言保留各自规则；定义、调用归属、文本调用作用域三者
  共用同一个 module QN，保证一致。
- 节点主键是 `qualified_name`（QN）；跨文件解析（`registry`、`pass_calls`、
  `pass_lsp_cross`）全部以 QN 为骨。语言差异只允许体现在 QN 的拼装规则与节点
  `label`/`properties` 上，不允许外溢到图 schema。

## 4. 并发、内存与稳健性

- **并行**：`src/pipeline/worker_pool.c` 是 pthreads + 原子 work-stealing 索引的
  通用 parallel-for；每个 worker 拿自己的 `gbuf` 抽取，随后
  `cbm_gbuf_merge()` 按 QN 合并（同 QN 时 src 覆盖 dst，边按 key 去重）。
- **线程本地资源**：每线程复用一个 `TSParser`（`get_thread_parser`，按语言重绑）、
  一个抽取 scratch arena、若干旋转缓冲区；避免大仓上反复创建/销毁解析器。
- **预算与降级**：每文件解析预算（CPU deadline + wall ceiling）；统一 walk 有节点数
  预算（`walk_budget_nodes`），超限置 `walk_truncated` 并跳过 LSP，而不是让整次索引失败。
- **崩溃隔离**：崩溃/hang 的文件被 supervisor 记入 quarantine 列表
  （`CBM_INDEX_QUARANTINE_FILE`，S/D marker 日志），后续索引对该文件直接短路，
  保证"一个坏文件不会反复杀死索引"。
- **内存**：结果 compact（`cbm_result_compact`）与 spill（`result_spill.c`）；
  抽取期的大数组与字符串统一走 arena，随结果整体释放。
- **取消**：`check_cancel` 贯穿各阶段；取消时保留上一代数据库。

## 5. 图模型与存储

- `src/graph_buffer/`：内存图。节点含 label/name/QN/行号/properties，以及
  TrackerV2 身份的七个专用字段（见下）；边按去重键去重（键含 source/target/type，
  以及 import 的 `local_name` 等区分维度，与 SQLite 侧的 UNIQUE 约束保持同步）。
- 后处理 pass（`src/pipeline/pass_*.c`）在内存图上补边：调用解析、类型引用、
  配置关联、路由、跨仓、相似度、语义、复杂度、测试、重要度、HashUID。
- `src/store/store.c`：SQLite 存储，`nodes`/`edges` 为核，另有 `projects`、
  `file_hashes`、`lsp_surface`、`index_coverage*`、`project_summaries` 等。
  索引格式版本 `CBM_INDEX_FORMAT_VERSION`（当前 **v2**）：v2 把 TrackerV2 身份从
  `properties` JSON 迁到了真实列 —— `hashuid / canonical_signature / condition /
  logical_module / duplicate_fingerprint / type_id / language_type_id`，并对
  `(project, hashuid)` 建唯一索引（NULL 豁免）。
- 写路径有两条：全量 dump 经 `internal/cbm/sqlite_writer.c` 批量写；增量/
  查询经 `src/store/` 的语句缓存。两者 schema 必须保持一致（代码注释反复强调）。
- 语言维度在存储侧只以两种形式出现：节点的身份列 `language_type_id`，
  以及 `get_architecture` 统计时按扩展名反推的语言名（`store.c` 的表驱动映射）。
  没有"每语言一张表"。

## 6. 对外消费面

- MCP（`src/mcp/mcp.c`）：`search_graph`、`trace_path`、`query_graph`（Cypher）、
  `get_code_snippet`、`get_architecture`、`check_index_coverage`、`detect_changes`、
  `get_by_hashuid`（TrackerV2 身份查询）等；工具注册与参数 schema 都在这一个文件里。
- CLI（`src/cli/`）：`index_repository`、`index_status`、查询类子命令等。
- 守护进程（`src/daemon/`）与图 UI（`src/ui/`、`graph-ui/`）。
- 查询侧不感知语言：图是统一 schema，语言差异体现在节点属性与身份列。

## 7. 扩展实践

### 7.1 新增一门语言（checklist）

1. 把语法放进 `internal/cbm/vendored/grammars/<lang>/`（含 `parser.c`，如有
   `scanner.c` 一并放）。
2. 新增包装文件 `internal/cbm/grammar_<lang>.c`：
   `#include "vendored/grammars/<lang>/parser.c"`。
3. 在 `internal/cbm/cbm.h` 的 `CBMLanguage` 枚举里加成员（保持数组顺序约定）。
4. 在 `internal/cbm/lang_specs.c`：加 `extern` 工厂声明、各节点类型名数组，
   以及 `[CBM_LANG_<X>] = {...}` 表行；`_Static_assert` 会检查数量一致性。
5. 在 `src/discover/language.c` 注册扩展名/文件名（必要时在 `userconfig.c` 的
   语言名反查表里补名字）。
6. 只有结构语义特殊时，才在 `internal/cbm/extract_defs.c` 等文件加语言分支，
   或新增专用抽取器。
7. 测试：`tests/test_lang_contract.c`（per-language 图契约，走**完整流水线**到真
   SQLite，断言节点/边类型存在、调用归属正确、不崩溃）+ `tests/test_grammar_*.c`；
   语法行为可参考 `tests/` 下的 grammar probe 系列。
8. 构建无需改 `Makefile.cbm`（`GRAMMAR_SRCS` 是 wildcard）；跑一次全量索引冒烟 +
   语言契约套件。

### 7.2 给某种语言加"语言相关"的后处理

- 挂载点：`pipeline.c` 的 `run_predump_passes()` 表（加一行即可）或
  `run_sequential_pipeline()` 的 `seq_passes` / 并行路径的对应 pass。
- 若只在某些模式跑，用表里的 `moderate_only` 语义或显式 `p->mode` 判断。
- 若依赖"整图完整"（如 HashUID 的容器链），必须确认增量三条路线各自是否满足，
  参照 `score_importance` 的判定方式。

### 7.3 语言扩展的实际案例：HashUID 多语言

TrackerV2 身份（HashUID）目前是 **Java-only**（`src/pipeline/pass_hashuid.c`，
详见 `docs/JAVA-HASHUID.md`）。扩展到多语言时，改动集中在这几处：

1. **节点需要语言标记**：图和 store 现在没有 node-level language 列，
   `language_type_id` 只在有身份时才有值；需要在 `pass_definitions.c` 的
   `build_def_props()`（提取期能拿到 `files[i].language`）写一个语言属性，
   或在 pass 里用 `cbm_language_for_filename()` 反推。
2. **把 Java 逻辑抽成 per-language 规格**：`pass_hashuid.c` 里硬编码了
   `language_type_id=2` 与 type_id `2/3/20/22/23`、靠 `hasBody` 属性判定
   "是不是 Java"、`signature` 取自 QN 尾巴、`logical_module` 走容器链、
   `condition` 恒空、`duplicate_fingerprint` 来自提取期 `declHash`。
   这些应外提为 `{language_type_id, 类型映射, signature 规则, condition 规则,
   logical_module 规则}` 的规格表。
3. **提取期补齐每语言元数据**：C 的 `condition` 必须在 **raw 树**上抓嵌套
   `#ifdef/#if/#else` 链（C/C++ 的预处理第二遍会把条件消解掉），
   `declHash`（声明文本 SHA-256）目前也只有 Java 路径在算。
4. 权威口径参考 TrackerV2：`LanguageType`（C=1 / JAVA=2 / PYTHON=3 / CPP=4）与
   `IdentifierType` 全局类型表；C 的具体语义（`signature=""`、`logical_module=""`、
   condition 归一化与 include guard 抑制）在 osana 侧已有实现可对照。

## 9. 设计要点与常见陷阱

- **表驱动优先**：语言的新增首先表达为 `lang_specs.c` 的一行；分支是例外而非常态。
- **枚举与表必须同序**：`CBMLanguage` 的下标就是数组下标，改动顺序会让整套映射错位；
  `_Static_assert` 只保证数量，不保证语义顺序。
- **行号有语义**：定义/调用行号是 1-based（`+ TS_LINE_OFFSET`）；C/C++ 预处理第二遍
  产生的是 expanded 行号，必须经 `original_line_by_expanded_line` 映射回原文，
  且 `belongs_to_main_file` 之外的宏展开内容不进入图。
- **嵌入式语言**：Vue/Svelte/Astro 等的脚本内容由 `embedded_imports` 重解析；
  改这些语言的抽取时，要同时验证宿主与嵌入两层。
- **模式门**：宏节点只在 FULL 抽取；相似度/语义边在 FAST 跳过；这些门槛写在
  `pipeline.c` 与各自的 `cbm_*_enabled()` 开关里，不要把语言能力错误地当成
  "所有模式都有"。
- **增量能力差异**：closure-delta 不产出 HashUID（容器可能缺失），设计任何依赖
  "全图完整"的 pass 时都要照这个先例判断可否在增量路线运行。
- **统一 schema 是底线**：语言差异不应新增表或改变查询接口；需要新信息时优先
  进 `properties` 或已预留的列，改 schema 就要走索引格式版本升级。
